# 第五章 传输层

## 5.1 传输层提供的服务

### 1. 概述

传输层向它上面的应用层提供通信服务，它属于**面向通信部分的最高层**，同时也是**用户功能中的最低层**。

### 2. 传输层的功能

- 提供应用进程之间的**逻辑通信**（即端到端的通信），使应用进程无需关注低层网络细节。
- **复用与分用**：
  - 复用：发送方不同的应用进程，可共用同一个传输层协议传送数据。
  - 分用：接收方的传输层剥去报文首部后，能将数据正确交付到目的应用进程。
- **差错检测**：对收到的报文（首部+数据部分）进行差错检测，确保数据完整性。
- **提供两种传输协议**：面向连接的TCP和无连接的UDP，满足不同可靠性需求。
- **屏蔽低层细节**：向高层用户屏蔽低层网络核心细节（如网络拓扑、路由协议等），使应用进程仿佛在两个传输层实体间有一条端到端的逻辑通信信道。

### 3. 传输层的寻址与端口

#### （1）端口的作用

- 标识主机中的应用进程，是传输层与应用层的“接口”。
- 实现数据交付：应用进程通过端口将数据下交给传输层，传输层通过端口将数据上交给对应应用进程。
- 端口号仅具**本地意义**：因特网中不同计算机的相同端口无关联。

#### （2）软件端口与硬件端口

| 类型     | 定义                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| 软件端口 | 协议层间的抽象协议端口，是应用层进程与传输实体的交互地址，传输层使用软件端口。 |
| 硬件端口 | 不同硬件设备进行交互的物理接口（如网卡端口）。                                 |

#### （3）端口号的分类

端口号范围为0~65535，分为三类：

1. **熟知端口号（0~1023）**：服务端固定使用，需IANA（互联网数字分配机构）分配，常见如下：
   - FTP（文件传输协议）：21
   - TELNET（远程登录协议）：23
   - SMTP（简单邮件传输协议）：25
   - DNS（域名系统）：53
   - TFTP（小文件传输协议）：69
   - HTTP（超文本传输协议）：80
   - SNMP（简单网络管理协议）：161
2. **登记端口号（1024~49151）**：需在IANA登记，防止重复，供特定应用使用。
3. **客户端端口号（49152~65535）**：又称“短暂端口号/临时端口号”，仅在客户进程运行时动态分配，通信结束后释放，可复用。

### 4. 套接字（Socket）

- 背景：网络中需通过“主机标识+进程标识”定位通信端点，IP地址标识主机，端口号标识主机内进程。
- 定义：**套接字 =（主机IP地址，端口号）**，唯一标识网络中一台主机及其上的一个应用进程，本质是一个通信端点。

### 5. 无连接服务与面向连接服务

#### （1）两种服务的核心差异

| 服务类型     | 建立连接 | 通信过程监控 | 资源释放   | 交付可靠性         |
| ------------ | -------- | ------------ | ---------- | ------------------ |
| 面向连接服务 | 需先建立 | 实时监控管理 | 通信后释放 | 可靠（需额外机制） |
| 无连接服务   | 无需建立 | 无监控       | 无需释放   | 尽力而为（不可靠） |

#### （2）TCP/IP协议族的传输协议

- **面向连接的传输控制协议（TCP）**：
  - 在IP层（不可靠）之上提供**全双工的可靠逻辑信道**，需额外实现确认、流量控制、计时器、连接管理等机制（开销较高）。
  - 适用场景：可靠性优先，如FTP、HTTP、TELNET等。
- **无连接的用户数据报协议（UDP）**：
  - 在IP层之上仅增加“复用/分用”和“差错检测”两个基础服务，提供**不可靠的逻辑信道**（开销低）。
  - 适用场景：实时性优先，如TFTP、DNS、SNMP等。

#### （3）TCP与网络层虚电路的区别

- 网络层若用虚电路：需所有交换节点保存虚电路状态，无法提供无连接服务；
- 传输层TCP：报文段在抽象逻辑信道中传输，对路由器不可见，不影响网络层提供无连接服务。

## 5.2 UDP协议

### 1. UDP协议的核心特点

- 简单高效：执行速度快、实时性好，首部开销小（仅8字节）。
- 无连接：无需建立连接，无连接时延；不维护连接状态，服务器可支持更多客户端。
- 面向报文：以“报文”为最小处理单位，应用层交付的数据直接封装为UDP数据报（不拆分/合并）。
- 尽最大努力交付：不保证可靠传输，丢包、乱序需应用层处理；接收方无需向发送方确认。

### 2. UDP的实现功能

在IP数据报服务基础上，仅增加两项核心服务：

- 复用与分用：通过端口号实现多应用进程的数据区分与交付。
- 差错检测：通过校验和检测数据报在传输中的错误（有错则丢弃）。

### 3. UDP数据报与IP数据报的区别

| 数据报类型 | 传输层级 | 路由可见性                   | 转发方式       |
| ---------- | -------- | ---------------------------- | -------------- |
| IP数据报   | 网络层   | 路由可识别（需存储转发）     | 路由器逐跳转发 |
| UDP数据报  | 传输层   | 路由不可见（封装为IP数据报） | 端到端逻辑传输 |

### 4. UDP的首部格式

UDP数据报由“首部（8字节）+数据”组成，首部含4个字段（各占2字节）：

- **源端口**：发送方端口号，需回信时使用，无需则填0。
- **目的端口**：接收方端口号，是终点交付的关键标识。
- **长度**：UDP数据报总长度（首部+数据），最小值为8（仅首部）。
- **校验和**：可选字段（不计算则填0），用于检测传输错误（有错则丢弃）。

### 5. UDP校验机制

- 校验范围：UDP首部+数据部分（若数据长度为奇数，需补1个全0字节再校验）。
- 伪首部辅助：校验时引入“IP伪首部”（含IP源地址、目的地址等），可同时检查IP层地址是否错误。
- 错误处理：校验出错时，可丢弃数据报，或交付上层并报告错误（检错能力较弱，但处理速度快）。

### 6. UDP数据报的交付与处理

- 正常交付：接收方UDP根据“目的端口号”，将数据报通过对应端口上交给应用进程。
- 错误处理：若目的端口号不存在，接收方丢弃数据报，并通过ICMP向发送方发送“端口不可达”差错报文。

## 5.3 TCP协议

### 5.3.1 TCP协议的特点与TCP报文段

#### 1. TCP协议的核心特点

- 面向连接：通信前需建立TCP连接，通信后需释放。
- 点对点通信：每条TCP连接仅支持两个端点（一对一），不支持多播/广播。
- 可靠交付：保证数据无差错、不丢失、不重复、按序到达。
- 全双工通信：连接两端均有“发送缓存”和“接收缓存”，可同时收发数据。
- 面向字节流：将应用层数据视为“字节流”，拆分/合并为TCP报文段传输（报文段是TCP的传输单元）。

#### 2. TCP报文段的首部格式

TCP首部最小长度为20字节（含固定字段），选项字段长度可变，核心字段如下：

| 字段名称             | 长度 | 作用描述                                                                                                                                                                                                                                         |
| -------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 源端口/目的端口      | 各2B | 标识发送方/接收方应用进程，实现复用与分用。                                                                                                                                                                                                      |
| 序号                 | 4B   | 标识本报文段数据的第一个字节的序号（TCP面向字节流，每个字节均有序号）。                                                                                                                                                                          |
| 确认号               | 4B   | 期望收到对方下一个报文段的第一个字节的序号（累计确认）。                                                                                                                                                                                         |
| 数据偏移（首部长度） | 4位  | 指出数据部分与报文段起始处的距离（单位：4字节），最大首部长度为60字节。                                                                                                                                                                          |
| 保留字段             | 6位  | 预留未来使用，默认填0。                                                                                                                                                                                                                          |
| 控制位（6个标志）    | 6位  | 关键标志：`<br>`- URG=1：紧急数据需优先传输；`<br>`- ACK=1：连接建立后必置1（确认有效）；`<br>`- PSH=1：接收方立即交付应用进程；`<br>`- RST=1：连接出错，需释放重连；`<br>`- SYN=1：连接请求/接收报文；`<br>`- FIN=1：请求释放连接。 |
| 窗口                 | 2B   | 告知对方允许发送的最大字节数（流量控制的核心字段）。                                                                                                                                                                                             |
| 校验和               | 2B   | 校验范围：首部+数据（需引入伪首部）。                                                                                                                                                                                                            |
| 紧急指针             | 2B   | URG=1时有效，指出紧急数据的字节数（紧急数据在数据部分最前面）。                                                                                                                                                                                  |
| 选项                 | 可变 | 如“最大报文段长度（MSS）”，需填充字段使首部长度为4字节的整数倍。                                                                                                                                                                               |

### 5.3.2 TCP连接管理

TCP连接管理包括**连接建立**、**数据传送**、**连接释放**三个阶段，核心是通过“握手”实现双向确认。

#### 1. 连接建立：三次握手（Three-Way Handshake）

目的：确保双方均能收发数据，并协商初始序号、缓存大小等参数。

1. **客户端→服务器**：发送“连接请求报文段”，参数：SYN=1（同步），seq=x（客户端初始序号x）。
2. **服务器→客户端**：同意连接，发送“确认报文段”，参数：SYN=1，ACK=1（确认），ack=x+1（确认客户端序号），seq=y（服务器初始序号y）；同时为连接分配缓存和变量。
3. **客户端→服务器**：发送“最终确认报文段”，参数：ACK=1，seq=x+1（客户端序号更新），ack=y+1（确认服务器序号）；客户端分配缓存和变量，连接建立。

#### 2. SYN洪泛攻击（SYN Flood）

- 攻击原理：利用TCP三次握手漏洞，攻击者发送大量SYN=1的连接请求（第一步），但不回复服务器的确认报文（第二步），导致服务器维持大量“半连接状态”。
- 危害：半连接会消耗服务器CPU和内存，最终导致服务器无法处理正常请求，甚至死机。

#### 3. 连接释放：四次挥手（Four-Way Wavehand）

目的：确保双方数据均已发送完毕，安全释放连接资源。

1. **客户端→服务器**：客户端主动关闭，发送“连接释放报文段”，参数：FIN=1（终止），seq=u（客户端当前序号u）；客户端停止发送数据。
2. **服务器→客户端**：服务器确认释放请求，发送“确认报文段”，参数：ACK=1，seq=v（服务器当前序号v），ack=u+1（确认客户端序号）；此时服务器仍可发送数据。
3. **服务器→客户端**：服务器发送完所有数据后，发送“连接释放报文段”，参数：FIN=1，ACK=1，seq=w（服务器当前序号w），ack=u+1。
4. **客户端→服务器**：客户端确认释放，发送“确认报文段”，参数：ACK=1，seq=u+1，ack=w+1；服务器收到后释放连接，客户端等待超时后也释放连接。

### 5.3.3 TCP可靠传输的实现机制

TCP通过**序号**、**确认**、**重传**三大机制，在不可靠的IP层之上实现可靠传输。

#### 1. 序号机制

- 核心：为字节流中的每个字节分配唯一序号，报文段的“序号字段”标识其数据部分第一个字节的序号。
- 作用：确保接收方按序重组数据，解决“乱序”问题。

#### 2. 确认机制

- 核心：接收方通过“确认号字段”告知发送方“期望下一个接收的字节序号”，默认使用**累计确认**（仅确认到第一个未丢失字节为止的所有数据）。
- 作用：让发送方知晓哪些数据已被成功接收，解决“丢失”问题。

#### 3. 重传机制

触发重传的两种场景：

- **超时重传**：发送方为每个报文段设置计时器，若计时器到期未收到确认，则重传该报文段（超时时间需动态调整，与往返时延RTT相关）。
- **冗余ACK重传**：若发送方连续收到3个对同一报文段的重复确认（冗余ACK），则判定该报文段已丢失，立即重传（无需等待超时，减少延迟）。

### 5.3.4 TCP流量控制

#### 1. 流量控制的目标

匹配“发送方的发送速率”与“接收方的接收速率”，防止接收方因缓存溢出而丢失数据（点对点控制）。

#### 2. 实现机制：滑动窗口协议

- 接收方根据自身“接收缓存”大小，动态调整发送方的“发送窗口上限”（即**接收窗口rwnd**），并通过TCP报文段的“窗口字段”告知发送方。
- 发送方的实际发送窗口大小 = min[接收窗口rwnd，拥塞窗口cwnd]（cwnd由拥塞控制决定）。

#### 3. 与数据链路层流量控制的区别

| 对比维度     | 传输层流量控制                   | 数据链路层流量控制         |
| ------------ | -------------------------------- | -------------------------- |
| 控制范围     | 端到端（应用进程之间）           | 相邻结点之间（链路层）     |
| 滑动窗口特性 | 窗口大小可动态调整（随缓存变化） | 窗口大小固定（配置后不变） |

### 5.3.5 TCP拥塞控制

#### 1. 拥塞控制的目标

防止过多数据注入网络，避免路由器/链路过载，保证网络整体传输性能（全局性控制）。

#### 2. 与流量控制的区别

| 对比维度 | 拥塞控制                       | 流量控制                   |
| -------- | ------------------------------ | -------------------------- |
| 控制范围 | 全局性（涉及所有主机、路由器） | 点对点（仅发送方与接收方） |
| 控制目标 | 避免网络过载                   | 避免接收方缓存溢出         |
| 决策依据 | 网络拥塞程度（如时延、丢包）   | 接收方缓存剩余空间         |

#### 3. 核心概念：拥塞窗口（cwnd）

- 定义：发送方根据网络拥塞程度估计的“最大可发送字节数”，大小与网络带宽、往返时延相关。
- 作用：限制发送方的发送速率，避免加剧网络拥塞。

#### 4. 拥塞控制的四大算法

TCP通过“慢开始、拥塞避免、快重传、快恢复”四种算法动态调整cwnd，平衡传输效率与网络稳定性。

##### （1）慢开始（Slow Start）

- 初始化：cwnd=1（1个MSS，最大报文段长度）。
- 增长规则：每收到一个确认，cwnd+1；每经过一个RTT（传输轮次），cwnd加倍（指数增长）。
- 切换条件：当cwnd达到“慢开始门限ssthresh”时，切换为“拥塞避免”算法。
- 目的：避免初始发送速率过高导致网络拥塞。

##### （2）拥塞避免（Congestion Avoidance）

- 增长规则：cwnd按“线性增长”（加法增大），每经过一个RTT，cwnd增加1个MSS（而非加倍）。
- 拥塞处理：若出现“超时重传”（判定网络拥塞），则：
  1. ssthresh = 当前cwnd / 2（乘法减小，降低门限）；
  2. cwnd重置为1，重新执行“慢开始”。

##### （3）快重传（Fast Retransmit）

- 触发条件：发送方连续收到3个对同一报文段的冗余ACK（判定该报文段丢失，非网络拥塞）。
- 动作：立即重传丢失的报文段，无需等待计时器超时，减少重传延迟。

##### （4）快恢复（Fast Recovery）

- 适用场景：配合快重传使用（非超时导致的丢包）。
- 处理步骤：
  1. ssthresh = 当前cwnd / 2（乘法减小）；
  2. cwnd = ssthresh（跳过慢开始，直接进入拥塞避免）；
  3. 按“拥塞避免”规则线性增长cwnd。
- 目的：在非严重拥塞场景下，快速恢复传输速率，提升效率。
